# ADR 0006: 存储层单一写者与进程内缓存

- 状态：Accepted（2026-09-11 架构巡检 grilling 决策）
- 决策者：项目负责人 + 执行 Agent

## 背景

`projects.json` / `settings.json` 的写操作此前都是「每次命令独立 load → 改 → save」，
命令层不持有任何共享状态（`lib.rs` 未注册 `State`）。Tauri 命令在线程池中并发执行，
两次重叠的写会各自基于旧快照落盘，产生丢失更新（lost update）。当前靠 UI 用模态框
串行化写操作兜底，属隐式约束而非架构保证。

## 决策

- 新增 `project::handle::JsonHandle<T>`：以 `Mutex<Option<T>>` 实现的单一写者句柄，
  首次访问时从磁盘加载并缓存，之后所有读写经由同一把锁。
- 写操作在锁内 clone → 调用用户闭包 → 保存成功后才提交回内存（事务语义：
  闭包或保存失败则内存状态不变）。
- `lib.rs` 在 `.setup()` 中解析数据目录并 `app.manage()` 两个句柄
  （`JsonHandle<Store>`、`JsonHandle<Settings>`）；命令层通过 `State` 取用。
- `*_in(data_dir, ...)` 参数化内核保留，供集成测试直接调用。

## 权衡与后果

**收益**：并发写不再互相覆盖；并发语义收敛到一个可测试的 seam；命令层退化为薄封装。

**代价**：

- 运行期间外部直接编辑 `*.json` 不会被感知（进程内缓存）。数据目录固定为 EXE 相邻
  （ADR 0004），且实现假定单实例运行，故接受。
- 多实例同时运行不受保护（进程内锁管不到跨进程）；如需彻底解决需引入单实例插件，
  暂缓（见实施计划备注）。
- 损坏文件的可诊断错误仍在首次访问时返回，行为与改动前一致。

## 替代方案被拒原因

「写锁 + 每次 load」改动更小，但每次写仍读盘，且没有把「单一写者」表达为一个模块；
「维持现状」仍把正确性交给 UI 习惯，不构成架构保证。
