# ADR 0007: 路径查重以服务端为权威，且仅接受绝对路径

- 状态：Accepted（2026-09-11 架构巡检 grilling 决策）
- 决策者：项目负责人 + 执行 Agent

## 背景

D3 路径查重在后端 `project::dedup::normalize_path` 有完整词法规范化（统一分隔符、
解析 `.`/`..`、去尾分隔符），而前端 `lib/paths.ts::samePath` 只覆盖其中一部分
（不解析 `.`/`..`、不做相对路径绝对化）。同一规则存在两个强度不同的实现，
前端注释虽称「与后端同口径」，实际并不成立；此外 `normalize_path` 对相对路径以
EXE 所在目录为基准绝对化，语义不直观。

## 决策

- 路径查重以后端为唯一事实源：新增只读命令 `check_path_available(path, excludeId)`，
  Add / Edit 对话框的前置校验改调该命令；删除前端 `samePath` 规则副本。
- `create_project` / `update_project` 在入口拒绝非绝对路径，返回可诊断错误。
- `normalize_path` 保留分隔符统一与 `.`/`..` 词法解析，但只作用于已确认的绝对路径。
- `projects.json` / `settings.json` 的数据格式与磁盘位置不变。

## 权衡与后果

**收益**：查重口径单源化，消除前后端漂移；相对路径不再有隐式基准。

**代价**：Add / Edit 的查重校验由同步变为异步（调用命令），需处理「校验中」的按钮态；
用户不能再输入相对路径（本应用此前也依赖文件选择器给出绝对路径）。

## 替代方案被拒原因

「保留前端副本但补齐 `.`/`..`」仍留两份实现，漂移风险不除；
「维持现状」等于接受一条注释承诺与实际不符的规则。
