A. 缺陷与风险

按「会不会造成用户可见错误」排序，而非按文件顺序。每条含证据、影响与修复方向。

A1 · 存储层「读-改-写」无单一写者，存在丢失更新风险

Medium · 潜在正确性
src-tauri/src/project/store.rssrc-tauri/src/commands/project.rssrc-tauri/src/commands/actions.rssrc-tauri/src/lib.rs
问题

每个写命令（create / update / delete / update_settings）都独立执行 Store::load(磁盘) → 改内存 → Store::save(磁盘)。Tauri 命令在线程池里并发执行，而 lib.rs 没有注册任何 .manage(...) 共享状态。两次重叠的写操作会各自基于旧快照落盘，后写者覆盖前写者 —— 典型的 lost update。当前 UI 用模态框把写操作基本串行化了，所以暂未暴露，但这是一个靠 UI 习惯兜底、而非靠架构兜底的隐患。

证据

project.rs 中 create_project_in / update_project_in / delete_project_in 均为「load → mutate → save」；lib.rs 全文无 .manage。

修复方向

在 Tauri state 中持有 Mutex<Store>（或 Mutex<()> 写锁 + 缓存），让所有变更经过同一个 StoreHandle 窄接口；磁盘 I/O 退化为「加载一次 + 每次变更落盘」。这同时把并发语义收敛到一个可测试的 seam。

A2 · 路径查重规则前后端双实现，且已出现口径不一致

Medium · 逻辑不一致
src-tauri/src/project/dedup.rssrc/lib/paths.tssrc/components/AddProjectDialog.tsx
问题

D3「路径查重」在后端有完整的词法规范化（统一分隔符、解析 ./..、相对路径绝对化、去尾分隔符），前端 samePath() 只做了「统一分隔符 + 去尾 + 小写」。前端代码注释也承认没有做 ./.. 解析。结果是同一条规则有两个强度不同的实现：D:\a\.\b 这类输入前端判为「不重复」，后端才拦截，用户会在 Step 2 才看到报错（错误信息与前端文案「同口径」的承诺不符）。

证据

dedup.rs::normalize_path（含 resolve_segments）vs paths.ts::samePath（无段解析）；AddProjectDialog.next() 用前端版本做「第一步即拦截」。

次要问题

normalize_path 对相对路径调用 std::env::current_dir()——在 Tauri 中 CWD 是 EXE 所在目录（见 ADR 0004），用户若手输相对路径，会以程序目录为基准绝对化，语义不直观。

修复方向

让查重成为服务端唯一事实源：新增只读命令 check_path_available(path, excludeId)，Add/Edit 对话框调用它做前置校验；删除 TS 侧的规则副本。

A3 · 「编辑器配置」校验规则被实现三次

Medium · 重复逻辑
src-tauri/src/project/settings.rssrc-tauri/src/launch/mod.rssrc/lib/theme.ts
问题

「{path} 占位符恰好出现一次」+「.cmd/.bat 参数不得含双引号」这条规则，存在于三处：EditorProfile::validate（settings.rs）、substitute_editor_path + validate_batch_arguments（launch/mod.rs）、validateEditorProfile（theme.ts）。连错误文案都是逐字复制。任何口径调整（例如将来允许多个占位符）都需要同步改三处，且没有任何机制保证它们一致。

证据

三处均出现字符串 "editor.arguments must contain exactly one {path} placeholder when editor.executable is configured"。

修复方向

后端收敛为 `EditorProfile` 上的单一深模块（validate + plan 一体），launch 复用同一校验；前端只在提交前做一次「预校验」，文案从共享常量取。

A4 · 默认值与枚举常量跨语言重复定义（6+ 处）

Medium · 漂移风险
src-tauri/src/project/settings.rssrc/lib/appearance.tssrc/lib/theme.tssrc/App.tsxsrc/components/SettingsDialog.tsx
问题

同一组「事实」在多处硬编码：

  • Windy 中性色：Rust default_light_neutrals()/default_dark_neutrals() vs TS WINDY_NEUTRALS（注释都写着「保持一致」）。
  • 风格预设 id：Rust STYLE_PRESETS = ["windy","cloud","ink","midnight"] vs TS STYLE_PRESET_IDS。
  • 强调色预设 id：Rust ACCENT_PRESETS vs TS ACCENT_PRESETS。
  • 默认 Settings 对象：App.tsx::DEFAULT_SETTINGS 与 SettingsDialog.tsx::DEFAULT_SETTINGS 各写一份（内容相同）。

跨语言重复无法完全消除，但目前是「靠注释约定」而非「靠结构保证」，属于典型的静默漂移点。

修复方向

（1）前端两个 DEFAULT_SETTINGS 合并为一个导出；（2）跨语言常量考虑由单一 JSON/生成器产出（例如把预设 id 与中性色落到一处构建期产物，Rust 与 TS 都消费），至少加一条「契约测试」断言两端的字面量相等，让漂移可被测试捕获。

A5 · 死代码 / 仅测试使用的导出

Low · 坏味道
src/lib/theme.tssrc/components/Icon.tsxsrc/lib/theme.test.tssrc/lib/iconUi.test.ts
问题
  • windowsBgrDwordToCss（theme.ts）：生产代码从未调用，只在 theme.test.ts 里被断言；真正的转换在 Rust windows_bgr_dword_to_css_hex。这是「为测试而存在的镜像实现」。

A6 · 契约测试是「读源码字符串匹配」而非行为测试

Low · 测试质量
src/lib/iconUi.test.ts
问题

iconUi.test.ts 通过 readFileSync 读 Icon.tsx/App.css 源码，断言其中包含某些子串。这类测试无法证明渲染结果正确，却会在无关重构（改名、换行、格式化）时误报，并且给「已覆盖 UI」的错觉。

修复方向

保留少量「可访问性契约」断言即可，其余改为组件行为测试（见 B6）。

A7 · hasExactKeys 每轮就地排序，且会改写传入数组

Low · 坏味道
src/lib/theme.ts
问题

keys.sort() 写在 .every() 回调里，每次迭代都调用一次（并就地改写调用方传入的数组）。当前因为 keys 都是当场新建的字面量所以没出问题，但既低效又容易被后人误用。

修复方向

排序移出回调，先 const sorted = [...keys].sort() 再比较。

A8 · 主题预览存在「双路径应用」与冗余 effect 依赖

Low · 坏味道
src/App.tsx
问题

previewSettingsTheme 既调用 previewTheme()（立即写 DOM 变量），又 setSettingsPreview() 触发一个会在下一帧再次 applyTheme 的 effect —— 同一份预览被应用两次。settingsPreviewState 被列进 effect 依赖，但 effect 函数体根本没读它。

修复方向

二选一：只保留 state 驱动的 effect（更符合 React 心智），或只保留命令式 previewTheme。清理无用依赖。

A9 · 单次扫描重复枚举同一目录（3 趟 read_dir）

Low · 性能
src-tauri/src/scanner/mod.rs
问题

scan_project_path 依次调用 detect_project_type、detect_tech_stack、detect_activity，其中 tech stack 与 activity（以及 has_file_with_ext）各自 read_dir 同一根目录。单项目多趟枚举，项目多、目录大时可省。

修复方向

扫描入口做一次 read_dir，把条目切片传给各检测函数。

A10 · 前端扫描结果缺少请求代际保护（与既有模式不一致）

Low · 一致性
src/App.tsxsrc/lib/settingsUi.ts
问题

设置相关的异步读取都用了 createRequestGeneration() 防竞态，但卡片扫描 scanOne 没有：快速连点「Rescan」时，较早的慢请求可能覆盖较新的结果；删除项目后到达的扫描结果也会写进 scans（无害但冗余）。既有抽象未被一致使用。

修复方向

scanOne 复用 createRequestGeneration，或改为按 id 记录代际。

A11 · 扫描类子进程无超时保护

Info · 硬化
src-tauri/src/git/mod.rssrc-tauri/src/commands/system.rs
问题

run_git 与 run_command_capture 都用 Command::output()，无超时。若 git/reg/where 挂起（网络盘上的 git、注册表被锁），会一直占住该命令线程。启动类命令受 ADR 0002 约束（detached、不等待），但扫描类没有对应约定。

修复方向

为扫描子进程加一个上限（例如 5s）并用 wait_timeout/kill 兜底，或至少记录此约束到 ADR。

B. 架构深化机会

使用 codebase-design 词汇（module / interface / depth / seam / adapter / leverage / locality）。每个候选给出「删除测试」判断与前后对比。

B1 · 拆分浅而巨大的 commands/system.rs

Strong
src-tauri/src/commands/system.rs (706 行 / 22 个 pub 项 / 5 类职责)
问题

一个模块同时承担：注册表文本解析、编辑器产品目录与发现、Windows 强调色读取、子进程捕获、路径规范化。接口面巨大（22 个 public 项），任何改动都要在这个 700 行文件里定位，locality 极差。其中纯函数（parse_registry_query_blocks、deduplicate_detected_editors……）已被大量测试覆盖，说明它们本可以是独立的深模块。

方案

按 seam 拆成 4 个窄而深的模块：system/registry.rs（解析）、system/editors.rs（产品目录 + 发现管线）、system/accent.rs（强调色）、system/exec.rs（子进程捕获）。detect_editors 只依赖这四者的窄接口。

收益（locality & leverage）

每个模块一个概念，改注册表解析不必再扫过强调色代码；子进程捕获（A11 的超时改造点）成为唯一收口；现有测试可原样平移，杠杆率不变而认知负担显著下降。

Before · 一个浅模块吞下 5 件事
commands/system.rs 706 行 ├ registry parse / editors / accent / exec / path └ 22 pub 项 · 改动半径 = 全文件
→
After · 4 个深模块 + 一个编排壳
system/registry.rs system/editors.rs system/accent.rs system/exec.rs detect_editors() 只做编排

B2 · 把「编辑器配置规则」收敛为一个深模块

Strong
src-tauri/src/project/settings.rssrc-tauri/src/launch/mod.rssrc/lib/theme.ts
问题

见 A3。规则的「接口」（validate + plan）被拆散在两个后端文件与一个前端文件里，且文案逐字重复。这是典型的浅 seam：调用方必须知道散落各处的约束。

方案

定义 EditorProfile 深模块：对外只暴露 validate() 与 plan(path) -> LaunchPlan，把占位符替换、批处理引号校验、cmd.exe 包装全部藏在实现里。launch 只调用 plan()，settings 只调用 validate()，两者是同一实现的两个入口。

收益

规则只存在于一处，「接口即测试面」—— 针对 plan() 的测试同时覆盖了校验与启动组装；将来扩展（多占位符、更多 shell）只改一个深模块。

Before · 同一规则三份实现
settings.rs::validate() launch::substitute_editor_path() launch::validate_batch_arguments() theme.ts::validateEditorProfile()
→
After · 一个深模块两个入口
EditorProfile::validate() EditorProfile::plan(path) ├ 占位符替换 ├ 批处理引号校验 └ cmd.exe 包装

B3 · 把 App.tsx 的状态编排抽成 hook 模块

Worth exploring
src/App.tsx (402 行 / 15 个 useState)
问题

App 组件同时持有 projects、scans、dialogs、toast、settings、settingsError、windowsAccent、preview 状态与四类副作用。这是整个前端唯一没有对应测试文件的「逻辑集中地」，任何一处改动都要在 400 行里往返。

方案

抽出 useProjects()（列表 + CRUD 乐观更新）、useScans()（扫描生命周期 + 代际保护，一并修 A10）、useSettings()（加载/保存/回退）、useThemePreview()（捕获/预览/还原，一并修 A8）。App 退化为布局与 props 装配。

收益

每个 hook 是可用 renderHook 测试的深模块；状态迁移的复杂度从「组件内隐式」变成「hook 接口显式」。这是提升前端 AI-navigability 性价比最高的一步。

B4 · 路径查重（D3）建立单一事实源

Worth exploring
src-tauri/src/project/dedup.rssrc/lib/paths.ts
问题

见 A2。纯前端副本是「假 seam」（one adapter = hypothetical）：它存在的唯一理由是为了更早报错，却带来了口径漂移。

方案

删除前端规则副本，改为调用只读命令 check_path_available。前端只负责触发与展示，规范化与比较完全由后端 dedup 这个深模块负责。

收益

删除测试成立：删掉 TS 实现后复杂度集中到唯一的 dedup，而不是被搬来搬去。测试面回到后端一处。

B5 · 简化 PowerShell 命令包装启发式

Speculative
src-tauri/src/launch/mod.rs
问题

quote_pwsh_command 及其辅助函数用约 150 行启发式判断「命令首段是不是路径」（盘符 / UNC / 相对 / 已知扩展名 / 真实存在的文件），再决定是否用 & '...' 包裹。它是 load-bearing 的（删掉则含空格路径会被 PowerShell 按空格切开），但复杂度与脆弱度都高，属于「为了兜底而过度设计」的临界点。

方案（待评估）

评估能否让用户把「可执行 + 参数」表达为结构化输入，从而用 PowerShell 的调用运算符/参数向量直接构造，而不是事后猜测纯文本。若产品上不接受结构化输入，则维持现状但把启发式收敛到单一纯函数并补齐边界测试（目前已有 38 项 launch 测试，基础良好）。

收益

若可简化，能消除一整类「命令文本被误切」的边缘 bug 面。

B6 · 为关键交互补组件测试 seam

Worth exploring
src/components/*.tsxsrc/pages/ProjectDetail.tsx
问题

当前 src/ 下测试全部落在 lib/（纯逻辑）+ 两个「读源码字符串」的契约测试；组件与页面零行为测试。而 Add 对话框的两步流程、Settings 的预览/还原/重置、ProjectCard 的降级渲染，恰恰是 bug 最易藏身处。

方案

用 Testing Library 为 AddProjectDialog（两步 + 查重拦截）、SettingsDialog（预览-取消-保存）、ProjectCard（loading/error/ok 三态）写行为测试。IPC 已由 api.ts 这层窄接口封装，mock 成本低 —— 这正是现有 seam 的红利。

收益

「接口即测试面」：这些组件的接口（props + 用户事件）清晰，适合作为测试面；同时让 A5/A6 里的源码字符串测试可以退役。

C. 首要建议

先修 A1（存储单一写者），再动 B1（拆分 system.rs），然后 B2/B4 去重。

为什么是 A1 先：它是唯一涉及数据正确性的问题，且修复方式恰好就是架构修复 —— 引入一个 StoreHandle 窄接口，既消除丢失更新，又把并发语义收敛成可测试的 seam。投入小、回报明确。

为什么 B1 第二：system.rs 是当前最大的「浅而巨大」模块，706 行、5 类职责、22 个 public 项，是认知与维护成本的主要来源；拆分是纯结构重构，现有 17 项模块测试可直接平移，风险低、性价比高。

为什么 A3/A4/B2/B4 一起看：它们本质是同一个病灶 —— 同一条规则/事实在 seam 两侧被复制。建议合并为一次「去重」工作流：后端建立 EditorProfile 深模块（B2）、路径查重单源化（B4）、契约测试锁住跨语言常量（A4），一次性把「靠注释保持一致」升级为「靠结构/测试保证一致」。

不必立刻做：B5（先做技术评估）、A11（硬化项）、A7/A8/A9（随手清理即可）。

方法：tsc --noEmit · vitest run · cargo test 全绿；随后对 src/ 与 src-tauri/src/ 逐文件人工通读，并结合 git log 热点（lib.rs / App.tsx / scanner / SettingsDialog）确定重点区域。 术语遵循 codebase-design（module / interface / depth / seam / leverage / locality），领域词遵循 CONTEXT.md。本报告不修改任何仓库文件。
